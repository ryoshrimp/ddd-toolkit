# facade 経由の実行可能なサンプル

[English](README.md) | 日本語

リポジトリのルートで次を実行してください。全例が facade のみを使い、`derive` feature
（既定で有効）を必要とし、assert で期待結果を確認します。追加依存、DB、ブローカー、
非同期ランタイムは不要です。

```sh
cargo build -p ddd-toolkit --examples --all-features --locked
cargo run -p ddd-toolkit --example basic --features derive --locked
cargo run -p ddd-toolkit --example cqrs --features derive --locked
cargo run -p ddd-toolkit --example event_sourcing --features derive --locked
cargo run -p ddd-toolkit --example reliable_delivery --features derive --locked
```

- [basic.rs](basic.rs): 注文を保存し、最初のイベントを配信した後に失敗させ、復元された
  バッチを再試行します。配信結果は `[1, 1, 2]`。保存は保留イベントを消費せず、
  配信失敗も保存をロールバックしません。
- [cqrs.rs](cqrs.rs): 加算ゼロを Specification、合計5000超過を Policy で拒否し、
  明示的なライフサイクルコールバックで保存・配信します。クエリ結果は4200です。
  簡単なクエリは Repository の状態を読み、別DBを必須としません。保存と配信は別操作です。
- [event_sourcing.rs](event_sourcing.rs): v1イベントをロード時にアップキャストして再生し、
  スナップショットを保存した後、`ExpectedRevision` を指定して追記します。古いリビジョンでの
  追記は状態を変えずに拒否します。スナップショット＋後続イベントも全履歴再生も結果は5、
  リビジョンは1（ゼロ始まり）です。アップキャストはアダプターのロード境界で行い、
  再生は保留イベントを記録しません。スナップショット利用後も全履歴を保持し、圧縮はしません。
- [reliable_delivery.rs](reliable_delivery.rs): 非同期アウトボックスのライフサイクルで口座保存と
  イベント投入を行います。ブローカー、チェックポイント保存、ack の失敗後も claim を再試行
  できます。安定したメッセージIDで重複排除し、3回の配信成功でもプロジェクション更新は1回
  （残高10）です。適用後、ack前にチェックポイントを保存します。保存失敗後の再適用は
  `AlreadyApplied` ですが、チェックポイントは再保存します。実ブローカーの consumer を動かす
  代わりにプロジェクションを直接呼びます。

## アダプターの責任範囲

すべての保存状態・重複排除状態は**インメモリ**で、プロセス終了時に失われます。
小さなアプリケーション側の実装例であり、toolkit 組み込みのアダプターや本番の永続性保証
ではありません。本番では以下が必要です。

- 集約状態とアウトボックスへの投入を、アダプターのトランザクションで原子的に永続化します。
  楽観ロックのリビジョン確認と追記も原子的に行います。ライフサイクルコンテキストだけでは
  DBトランザクション、ロールバック、クラッシュ復旧を提供しません。
- claim のリース、複数ワーカーの所有権、復旧、再試行・バックオフを定めます。
  この例は口座1つ・ワーカー1つで、ackまでキュー先頭を再claimします。
- at-least-once 配信を前提とします。配信成功後のack失敗で重複配信が起こります。
  プロジェクション更新と重複排除マーカーを原子的に永続化してください。
  別操作のチェックポイント保存が失敗しても再生で効果を二重適用しない設計が必要です。
- 永続カーソルの意味・順序を定めます。この例のカーソルは安定したメッセージIDであり、
  ソート可能なストリーム位置ではなく、大小比較もしません。
- 非同期契約はランタイムを選ばず、ボックス化した `Send` Future を返します。
  例の `ready` は1回だけpollして `Pending` を拒否するもので、汎用executorではありません。
  実I/Oにはアプリケーションでexecutorを選び、アダプターでキャンセル・エラー復旧を設計します。
  アウトボックスのライフサイクルは失敗・キャンセル時にもイベントバッチを消費します。
  コマンドや投入を無条件に繰り返すと効果の欠落・重複が起こり得るため、コミット結果が不確実な
  場合は、このヘルパーではなく永続的なアプリケーション／アダプターの復旧で解決してください。

CIは通常のワークスペーステストとfeature-matrixに加え、4例を明示的にビルド・実行します。
`required-features = ["derive"]` により、no-default-features の検査ではderive依存の例を除外します。
